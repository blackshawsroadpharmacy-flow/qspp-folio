## A1. Executive summary

QSPP Folio is a well-built single-owner tool: 451 source-derived requirements with provenance, strict identifier namespaces, separate state machines, an honest "this app does not award accreditation" stance, and a real offline posture (no outbound network except an optional loopback model server). Its biggest strength is that the data model and copy are disciplined about not overclaiming. Its biggest risk is the gap between that discipline and what the code enforces: a requirement can be marked Manager-verified with zero evidence (`QsppWorkspace.cs:120-144`), anyone at the login screen can reset the owner's passphrase (`AuthAndAudit.cs:163`), a restore overwrites the live database with no safety copy (`App.axaml.cs:526`), and the shipped app bundles the Standard and every program PDF with no evidence the rights to redistribute them exist. For the owner's own pharmacy this is a B-minus tool. As a $1,000/yr product for strangers it is a D-plus today: there is no licensing, no update path for the corpus or the app, no notarisation (a deliberate hold), and the OCR helper needs macOS 26 while the README says macOS 11+. **Buy test:** a pharmacist who reads only this paragraph should trial it on a scratch copy, not rely on it for a real assessment, and not pay until the three fixes below land.

Three highest-leverage fixes: (1) settle the right to ship the corpus and the QuestPDF licence position, then ship only what is allowed (FIX-01); (2) make "verified" mean something: readiness gated on reviewed evidence, close the retire and reset bypasses (FIX-02, FIX-05, FIX-06); (3) make upgrades and restores safe and give customers a corpus update path (FIX-03, FIX-04, FIX-07).

## A5. Compliance-domain correctness

### Identifier namespaces

Enforced where it matters: enum plus unique index plus kind-salted deterministic ids. Weak spots are string-only lookups (`QsppWorkspace.cs:571` finds `1.1.2.4` by `Ref` alone; `UnresolvedIssuesFor` matches `Ref.Contains("10")` at `:95`). Today no collision exists in the seed (one shared ref string, `Rule 49`, across RULE/OBLIGATION). Tests use Ref-only lookups (`Db.Requirements.First(r => r.Ref == "Rule 10")`), which will break the day a second kind reuses a ref.

### Coverage ledger

Seed (verified by me): 451 requirements; kinds UAGKeyTask 284, RULE 51, STD 40, UAG 26, TC 23, HITLIST 14, POLICY 8, OBLIGATION 5; zero missing `sourceDoc`, `sourceVersion`, `title`, `summary`, `wording`, `applicabilityHint`. 8 items carry `verify-todo`. 2 key tasks have `lettersVerified: false`. Schema does not enforce any of this (see matrix).

Import is one-shot for the corpus (`SeedImporter.cs:225`), issues (`:339`) and documents (`:419`). New program versions (a Program Rules V1.1, a new policy) never reach an installed pharmacy. Only two paths update existing installs: wording refresh (DD-35) and the REM upsert (`:100-165`). The REM upsert adds missing evidence examples but never rewords or retires existing ones (`:140-157`). A first-run import that dies midway leaves a partial corpus forever, because `db.Requirements.Any()` is then true (`:225`) and the failure is swallowed at `App.axaml.cs:136`. UNVERIFIED whether the import is one transaction.
